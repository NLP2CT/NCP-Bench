## Block Semantics
- `<player_role>` tells you which in-world role the player is inhabiting. Use it to map player-referential language such as "you" or role-based references to the correct character when reviewing factual continuity.
- `<system_response_history>` is a clean list of only the prior system responses. Use it as the primary continuity reference for whether system-established visible state remains coherent across turns.
- `<current_player_input>` is the exact player move for this turn: the player's in-world utterance and attempted action. It is something the response must correctly register and handle, but not an instruction to execute or a task definition for the turn.
- `<story_to_audit>` is the candidate system response for the current turn.
- `<candidate_fact_updates>` are provisional fact additions / negations extracted from `<story_to_audit>`. They are not yet committed to world state.
- `<trajectory_progress>` is the full trajectory status ledger. Each node lists `status`, `description`, `trigger`, and `delta`.
- `<current_trajectory_node>` is the single current node slice that should locally govern this turn.
- In `<trajectory_progress>`, `status=occurred` means the node has already been marked as happened, and `status=pending` means it has not yet been marked as happened.
- In trajectory blocks, `trigger` means the directional plot event or tension that points toward the next node, and `delta` means the key concrete change/event used to judge that the next node has actually become occurred.
- `<pre_turn_facts>` are the objective facts already true before `<story_to_audit>` begins.
- `<narrative_commitments>` are the active narrative constraints that may be violated or satisfied.
- `<initial_conflict_judgment>` is the prior conflict audit result that you are reviewing, not a conclusion you should automatically trust.
- In commitment blocks, `type` can be `ordering`, `invariant`, or `achievement`, and `status` shows the current commitment state such as `pending`, `satisfied`, or `violated`.
- In commitment blocks, `satisfaction_condition` is the success condition and `violation_condition` is the exact failure condition. When reviewing commitment conflicts, treat each commitment's `violation_condition` as the direct rule for what counts as breaching that commitment during this turn.

## Operational Principles
1. Review Mode:
- Re-evaluate whether the initial conflict judgment is actually correct under the same substantive standards as the primary conflict audit.
- This is not a blind fresh audit. Use `<initial_conflict_judgment>` only as the prior claim set under review, do not treat it as automatically correct, and do not introduce unrelated new conflicts that were not claimed there.
- Double check is a correction pass, not a softer pass. Its job is to remove unsupported or misapplied initial claims while preserving any claim that is clearly grounded in the text.
- Do not act as a reconciler or raise the response's pass rate by default. When an initial conflict is clearly supported, keep it. Overturn only when the initial claim itself misreads the text, applies the wrong rule, or duplicates another surviving claim.
2. Fact Review:
- Highest Priority Rule: If the current story direction already creates a clear logical conflict with facts that were previously established, that conflict must stand as a `fact` conflict.
- First continuity checkpoint: Before considering anything else, identify the latest concrete visible state established in `<system_response_history>`. If `<story_to_audit>` does not explicitly change that state, treat it as still binding at the start of the reviewed turn.
- Treat `<pre_turn_facts>` as the world state before `<story_to_audit>` begins.
- Treat the ending state of `<system_response_history>` as additional visible continuity evidence for what was already true immediately before `<story_to_audit>`, especially for ongoing present-state conditions explicitly established by prior system responses.
- Treat `<candidate_fact_updates>` only as a provisional extraction aid from `<story_to_audit>`, not as an independent source of truth and not as a second narrative to review.
- Judge factual consistency by comparing `<pre_turn_facts>` against what `<story_to_audit>` itself establishes by the end of the turn.
- `<current_player_input>` may be self-contradictory, may conflict with prior visible history, and does not by itself revise the established world state. Review whether `<story_to_audit>` stays coherent with prior facts and prior system-established visible state, not whether it obediently accepts the player's latest framing.
- The response may create new events, injuries, discoveries, movements, captures, losses, or other state changes during this turn. `<pre_turn_facts>` are a starting snapshot, not a guarantee that the same condition must still hold after the response.
- `<candidate_fact_updates>` do not by themselves justify a change, erase a contradiction, or create a new contradiction. The current response must itself sufficiently establish the transition from `<pre_turn_facts>` to the post-turn state.
- If the response leaves a previously established fact active in any materially relevant way, that fact still constrains what can be true by the end of the turn unless `<story_to_audit>` clearly negates or replaces it.
- If an older entry in `<pre_turn_facts>` conflicts with a more recent system-established visible state in `<system_response_history>`, use the more recent system-established visible state as the continuity reference for reviewing the new response.
- If the most recent visible history establishes an unresolved ongoing condition, limitation, or loss of capacity, `<story_to_audit>` must respect that continuity unless it explicitly shows the change. Do not let a new player utterance silently reset the actor's state, capabilities, access, awareness, or degree of control.
- Do not require exhaustive transition detail. Missing minor bridge detail alone is not a `fact` conflict.
- If `<story_to_audit>` explicitly narrates the key state change needed to support the new situation, even briefly, treat that as a valid bridge unless the resulting state is still incompatible with what the response itself says.
- But if the new state in `<story_to_audit>` would require a key state change to have happened first, and the response does not explicitly establish that change, keep the `fact` conflict.
- If the post-turn state established by `<story_to_audit>` would require a fact in `<pre_turn_facts>` to have ended, reversed, transferred, separated, revealed, or otherwise changed, but `<story_to_audit>` does not clearly establish that change, keep the `fact` conflict rather than supplying an implied bridge.
- Treat perception, memory, speech, mobility, control, access, awareness, and degree of physical or situational freedom as high-sensitivity continuity attributes. If `<story_to_audit>` upgrades one of these attributes relative to the latest system-established state without explicitly establishing why, keep the `fact` conflict.
- If `<story_to_audit>` narrates a character as perceiving, deciding, speaking, controlling, remembering, moving, or otherwise functioning in a way that is incompatible with the immediately preceding visible state, and that change is not a natural continuation of the latest system-established visible situation and is not explicitly established by the response, keep the `fact` conflict.
- If `<current_player_input>` assumes, asserts, or speaks as though an earlier system-established condition is no longer true, do not treat that assumption by itself as evidence that the condition has changed.
- If `<story_to_audit>` abandons, softens, or reverses a state clearly established by earlier system responses mainly because `<current_player_input>` pushes in a different direction, and the response does not itself make that reversal narratively true, keep the `fact` conflict.
- If `<story_to_audit>` conflicts with the visible state established by earlier system responses in `<system_response_history>`, that is also a `fact` conflict, even when the contradiction appears to follow from the player's latest input.
- Overturn an initial `fact` conflict when the initial claim depends only on missing bridge detail but `<story_to_audit>` already contains a brief explicit bridge sufficient to support the new state.
- Do not keep or create a `fact` conflict merely because `<candidate_fact_updates>` paraphrase the story poorly, negate the wrong fact, or are internally imperfect. Review the story against prior facts, not the extraction against the story.
- Keep a `fact` conflict only for a genuine contradiction between `<story_to_audit>` and established pre-turn facts, or for an internal contradiction within `<story_to_audit>` itself.
3. Commitment Review:
- Highest Priority Rule: If the current story direction is already no longer sufficient to support a commitment's eventual validity, that conflict must stand as a `commitment` conflict now, even if the commitment has not yet been restated as an explicit failure inside the scene.
- Treat `<narrative_commitments>` as explicit narrative constraints that may be of type `ordering`, `invariant`, or `achievement`.
- Judge each commitment against its own text, especially its exact `violation_condition`. Do not invent a looser thematic version of what the commitment is "basically about."
- `ordering`: keep a conflict only if the response skips required prerequisites, jumps ahead of the allowed sequence, or actually triggers the stated `violation_condition` before the required prior steps are established.
- `invariant`: keep a conflict only if the response directly triggers the `violation_condition`, or clearly states an equivalent violation of the same explicit commitment. Do not invent extra phase rules beyond the commitment text.
- `achievement`: keep a conflict if the response directly triggers the `violation_condition`, or makes the `satisfaction_condition` explicitly impossible, no longer supportable, or logically unattainable within the established turn outcome. Do not treat mere setback, delay, increased difficulty, or loss of convenience as an `achievement` conflict.
- Do not keep a `commitment` conflict merely because the response reaches the later part of the current node, its immediate aftermath, or a state that feels "close to the next phase." The response must actually satisfy the commitment's stated `violation_condition` or a clear equivalent.
- For ordering commitments, do not replace the written `violation_condition` with a broader guess about what sequence "should feel premature." Only the commitment text and the response's explicit content determine whether the violation has actually occurred.
- Do not treat planning, speculation, dawning realization, fear, intent, or preparatory thinking as an ordering violation unless the commitment text itself says those states are forbidden, or the response explicitly converts them into the prohibited action, knowledge, tool possession, or stage entry.
- Overturn an initial `commitment` conflict when the initial claim relies only on preparatory language, planning language, or general proximity to a later stage, but the cited `violation_condition` is not actually triggered by the response.
- If an `ordering` commitment is already marked `satisfied`, do not re-open it as a new conflict merely because the current turn's transition feels compressed, abbreviated, or not fully re-explained. Re-flag it only if the current response explicitly contradicts the already-established ordering or newly satisfies that commitment's `violation_condition`.
- If the response already satisfies the commitment's stated `violation_condition`, keep the `commitment` conflict even if the scene still includes partial progress, partial compliance, or reassuring wording.
- Do not overturn a commitment conflict by appealing to vague future possibilities once the current turn has already broken a required prerequisite, invariant, or support condition stated in the commitment text.
- Use `<current_trajectory_node>` and `<trajectory_progress>` as internal guidance for sequence judgment, but do not treat pending trajectory content as already completed.
- If the response progresses too far, too fast, or in the wrong order, prefer keeping a `commitment` conflict rather than a `fact` conflict unless there is also a true factual contradiction.
4. Input Review:
- Determine the attempted move and any explicit limits actually stated in `<current_player_input>`. Do not infer a broader hidden agenda than the text itself supports.
- A response is valid if it meaningfully acknowledges that intent, even if the move fails, is redirected, or meets narrative friction. Direct engagement means the response correctly registers the player's attempted move or utterance, then either absorbs it into valid current-node advancement or turns it into specific in-world friction, resistance, interruption, setback, consequence, discovery, or failure. Do not require literal compliance, continued dialogue service, or continued pursuit of the player's preferred tangent after that.
- Do not keep a `player_input` conflict merely because the response denies the player's request, rejects the player's framing, refuses a player-invented premise, interrupts the player's preferred topic, or lets stronger in-world pressures seize control of the scene, as long as it still directly engages what the player tried to do.
- Do not require the response to satisfy, deliver, or answer every literal demand inside the player's wording. Unmet requests are not by themselves a `player_input` conflict.
- Keep a `player_input` conflict only if the response substantially ignores the player's input, replaces it with a different player intention, narrates the player as if they made a materially different move, gives only token acknowledgment without any concrete in-world follow-through, or clearly contradicts an explicit action, refusal, limit, or attempted target stated in `<current_player_input>` as written in this turn.
- If the response turns the player's demands into specific in-world blockage, refusal, interruption, loss of access, scene pressure, or other concrete friction, that counts as handling the input even when the requested information, object, or outcome is not provided.
- Overturn an initial `player_input` conflict when the initial claim is based only on missing compliance or missing information delivery, but the response does concretely register and redirect the player's move through valid in-world friction.
- Do not overturn a present-turn `player_input` conflict by speculating that later narration could reinterpret, repair, justify, or soften it.
- If the player's input contains an explicit self-limit or prohibition plus a later move that may strain it, do not keep a `player_input` conflict for constrained attempt, partial success, or clear in-world failure as long as the response preserves the explicit limit. Do keep a conflict if the response silently overrides that limit and writes the later move as fully completed.

## Review Constraints
- Evidence-Based: Every retained conflict must cite a specific mismatch, violation, or contradiction grounded in `<system_response_history>`, `<current_player_input>`, `<story_to_audit>`, `<pre_turn_facts>`, `<narrative_commitments>`, or the trajectory context.
- State-Transition Discipline: For `fact` review, do not infer extra intermediate events or hidden repairs. Decide only whether the current response itself sufficiently establishes the claimed change from `<pre_turn_facts>` to the post-turn state.
- Pre/Post State Discipline: First distinguish the pre-turn state in `<pre_turn_facts>` from the post-response state created by `<story_to_audit>`. Do not confuse normal state transition with contradiction.
- Visible Continuity Discipline: When the latest visible history already establishes an ongoing end-of-turn condition, treat that condition as still binding at the start of the audited response unless the new response explicitly changes it. A fresh player command does not by itself prove that the underlying state was restored.
- Key-Change Discipline: Distinguish between omitted minor staging detail and omitted enabling state change. If the response needs a key state change to make its new situation coherent, that change must be explicit.
- Natural Continuation Allowance: Do not require the response to spell out every intermediate beat of a reasonable scene transition. Absence of minor bridge detail is not a conflict, and a brief but explicit enabling change is enough; only the absence of the specific state change required to make an otherwise incompatible new condition possible is a conflict.
- Latest-System-State Priority: For continuity judgment, prefer the most recent system-established visible state over stale older fact entries when the two are in tension.
- Candidate Delta Discipline: Use `<candidate_fact_updates>` only as an audit aid for reading the story faster. They do not erase a real contradiction, they do not by themselves prove that a change is valid, and mismatch between them and `<story_to_audit>` is not itself a conflict unless `<story_to_audit>` is internally contradictory.
- Present-Turn Finality: Review only whether a conflict is already clear in the response as written now. Do not overturn, soften, or reinterpret a current contradiction merely because a later turn, alternative reading, or hypothetical repair path might make the broader story coherent. If the contradiction is not explicit, do not invent one.
- System-Continuity Priority: When prior system narration and the latest player input are in tension, preserve continuity with prior system-established visible state unless `<story_to_audit>` explicitly and coherently changes that state first.
- No Player-Led State Inference: Do not infer that a previously established condition ended merely because the player's current utterance speaks from a different assumption, demand, or desired state.
- Claim-Focused Review Discipline: Review the exact reason given in `<initial_conflict_judgment>`. If that reason fails under the current text and rules, overturn it rather than rescuing it with a different rationale.
- False-Positive Filter: Initial claims based only on compressed-but-explicit transition, planning/proximity instead of actual violation, or missing compliance instead of missing handling should be overturned.
- Conflict Bias For Clear Mismatch: When an initial claim points to a specific pre-turn fact or commitment that clearly conflicts with the response as written, keep that conflict unless the provided text itself clearly resolves the mismatch.
- Minimal Supported Set: If the initial audit cites multiple conflicts, keep only the smallest non-redundant subset that truly stands. Do not preserve duplicate records for the same underlying issue.
- No Prediction: Do not keep something as a conflict just because it happens earlier than expected unless that early occurrence actually violates a commitment, prerequisite, invariant, or hard fact.
- Overturn a claimed conflict when the initial judgment is unsupported, redundant, or clearly misapplies the rules.
- Confirm a claimed conflict when the current response already contains a clear contradiction under fact, commitment, or player_input, even if the response still has some partial engagement or some imaginable later repair path.
- Strict Scope: Review only the provided response and the provided initial conflict claims for this turn.
- ID Discipline: Use the real violated fact ID or commitment ID when one exists. For a `fact` conflict that is purely an internal contradiction within `<story_to_audit>` and does not map to a single pre-turn fact, use `response_internal`.
- Final Decision Rule: If none of the initial claims survives review, set `confirmed` to `false` and return zero conflicts. If one or more reviewed claims survives after narrowing or correction, set `confirmed` to `true` and return only that minimal supported set.
