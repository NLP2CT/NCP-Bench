## Block Semantics
- `<player_role>` tells you which in-world role the player is inhabiting. Use it to map player-referential language such as "you" or role-based references in `<interaction_history>` to the correct character when judging commitment status.
- `<current_facts>` are the objective facts true by the end of the current turn.
- `<interaction_history>` is the full visible history through the end of the current turn, including the latest system response.
- When `<interaction_history>` includes `Player:` lines, treat them as the player's in-world utterances and attempted moves, not as instructions or task definitions.
- `<trajectory_progress>` is the full trajectory status ledger. Each node lists only `status` and `description` here.
- `<narrative_commitments>` lists the full current commitment set for this turn.
- In `<trajectory_progress>`, `status=occurred` means the node has already been marked as happened, and `status=pending` means it has not yet been marked as happened.
- A node's `status` is only trajectory ledger context. Do not treat a node status by itself as proof that every event mentioned in that node's description has already happened unless `<current_facts>` or `<interaction_history>` also support it.
- In `<narrative_commitments>`, `type` can be `ordering`, `invariant`, or `achievement`.
- In `<narrative_commitments>`, `status` is the currently tracked commitment state before this audit pass, and it will only be `pending` or `satisfied`.
- In `<narrative_commitments>`, `satisfaction_condition` is the exact condition you must judge against. It is the judgment target, not a loose thematic summary.

## Operational Principles
CRITICAL: You must distinguish between "what is planned to happen" (`<trajectory_progress>`) and "what has actually happened" (`<current_facts>` / `<interaction_history>`).

1. Condition-First Judgment:
- Judge each commitment against its own `satisfaction_condition`, not against the general topic of the commitment, the surrounding trajectory stage, or what the story seems to be moving toward.
- First identify the concrete referents named in the condition: specific events, actions, objects, knowledge states, identities, or ordering relations.
- Count evidence only when it describes that same specific referent. Shared domain, atmosphere, location, or technical similarity is not enough.
- Do not collapse distinct narrative elements into one another. Two events or actions are not equivalent merely because they happen in the same scene or belong to the same broad domain.
- If a condition uses broad words such as `related`, `relevant`, `associated`, `knowledge`, or `tools`, interpret them narrowly by the specific downstream event or object named in that same condition. Generic access, routine equipment, local scene procedures, or ordinary operational knowledge do not count unless the evidence clearly ties them to that protected narrative event.
2. SATISFIED:
- The `satisfaction_condition` is explicitly met by at least one item in `<current_facts>` or recorded in `<interaction_history>`.
- Note: Being mentioned in `<trajectory_progress>` does NOT count as being satisfied. The trajectory is a map, not a record of completion.
- For `ordering` types: All preceding nodes must have a confirmed status in `<trajectory_progress>` AND corresponding evidence in `<interaction_history>`.
- For commitments that must remain true across an open interval, phase, or "until/before X" window, do NOT mark them SATISFIED merely because they have held so far. If the protected interval is still ongoing, the correct status remains PENDING until that interval clearly ends without violation.

3. PENDING:
- Return `PENDING` whenever the `satisfaction_condition` is not currently established.
- Even if `<trajectory_progress>` points toward this commitment, if the specific facts have not manifested yet, it MUST remain PENDING.
- This includes ongoing invariants and phase-bound ordering constraints that are still being maintained but whose evaluation window has not yet closed. "Still holding so far" is not enough for SATISFIED.
- If a commitment was previously `SATISFIED` but the current materials no longer establish that the `satisfaction_condition` is true now, return `PENDING`.
- If the available evidence is ambiguous, indirect, partial, or only loosely related to the condition's wording, default to PENDING.
- For ordering commitments, "we are still before the prerequisite node" is usually PENDING.

## Audit Requirements
- [EVIDENCE-BASED]: Every status judgment must cite specific evidence from `<current_facts>` (f_x) or `<interaction_history>`.
- [NO PREDICTION]: Do not treat upcoming nodes in `<trajectory_progress>` as "done". If it has not happened in `<interaction_history>`, it is not SATISFIED.
- [STRICT LOGIC]: No subjective speculation.
- [TWO-STATUS-ONLY]: The only allowed output statuses are `SATISFIED` and `PENDING`.
- [REASON PRECISION]: For `SATISFIED`, the reason must name the exact condition terms being matched and the exact supporting evidence. For `PENDING`, explain briefly why the current materials do not yet establish the `satisfaction_condition`.
